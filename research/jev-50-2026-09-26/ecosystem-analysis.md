# Jev 案例分析：生态证据与万界门机会

调研日：2026-09-26。研究范围为公开资料；未运行社区项目、未购买 API、未验证商业采用量。本文不编制 50 项榜单，与主研究的案例表配套。

## 八个值得带进讨论的观察

1. **热门不等于需求最大。**《Jev in the Wild》作者报告：截至 9 月 22 日，样本含 2,170 个公开 GitHub 项目；路由/自动化与界面 Agent 合计占项目 19.6%，却占星数 63%。论文明确提醒，星数属于整个仓库，反映可见度，不证明存在未满足需求。这些数字是论文报告值，未独立重建其数据。[论文 §3.4](https://arxiv.org/html/2609.30216v1)

2. **组合值得研究，但论文不能证明产品已经成功。**论文报告，有明确用途的项目中 69.7% 同时承担多个决策目的。其纳入和分类依赖模型 Agent 及第二 Agent 复核；公开代码或文档证据不等于用户留存、付费或生产可靠性。正文链接中没有找到可下载的完整 2,170 项数据，因此不可从该论文直接声称“全球最火前 50”。[论文 §2.1、§3.2](https://arxiv.org/html/2609.30216v1)

3. **Jev 是组合里的判断部分；界面和内容仍需要真实的执行层。**官方把控制流程、确定性规则和副作用交给代码，模型处理范围清楚的语义判断。对于万界门，“这段输入更像要比较”之后，仍需取数、建立比较对象、选组件、连接交互、生成必要文本。这解释了为什么只把输入复制成文稿，即使实时调用了模型，仍没有实现用户想要的东西。[官方构建指南](https://docs.typesafe.ai/concepts/how-to-build-with-system-one.md)

4. **实时组合可以并行判断多个维度。**官方的 speculative fan-out 会一次提出类别、程度、是否缺条件等多个问题，收到后由代码采用相关答案，省去先分类再追问判断的串行往返。各问题独立读取同一个 state；它们不会自动共享前一个问题的答案。这里支持的是并行架构，不保证用户输入每个字都能在固定毫秒数内完成整个取数和渲染链。[并行判断](https://docs.typesafe.ai/patterns/fan-out.md)、[state](https://docs.typesafe.ai/concepts/state.md)

5. **语义选择和精确计算必须分别落地。**官方 jev-1.13 限制包括计算、日期比较、多层间接推理、无关长上下文和文本生成；Score 不能当连续物理量插值。商品预算、库存差额、日期冲突应由代码计算；Jev 判断哪条记录相关、哪种异常值得关注，生成模型再负责说明和写作。[已知限制](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md)

6. **格式正确不是判断正确，组件标签也可能影响选择。**官方提醒指令与 criteria 矛盾会导致误判；独立预印本通过交换选项名字与定义发现标签效应。该论文醒目的 70.4 点变化及 AUC .94→.23 属于开源 marker 模型，不能说成官方 Jev 结果。论文中 hosted Jev 的对应实验是 32.5% 答案翻转、AUC .8146→.5806；这是特定对抗式重映射实验，不是普通使用错误率，本文未复现。[官方限制](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md)、[研究 §4.6](https://arxiv.org/html/2609.26758v1)

7. **中文实时输入是单独的验收对象。**官方 state 文档称目前接受文本和文本 JSON，不接受原始图像、音视频；主要训练语言是英语，CJK 能输入但准确率较低。故拖图要先有 OCR/视觉处理，中文还应覆盖半句话、否定改口、拼音输入法和指代。官方 Jev 资料不能直接证明本项目本地 KEV 的性能。[输入与语言边界](https://docs.typesafe.ai/concepts/state.md)

8. **不确定性可以影响界面，而不只是写进日志。**官方 confidence 是概率分布的统计量，阈值需按任务评估。对万界门的产品推论：不确定时保留用户已操作的区域、展现一个小补充选项，比强制跳到错误整页更合适。这是设计假设；不能把 confidence 当成该答案正确的承诺。[置信度定义与使用](https://docs.typesafe.ai/confidence.md)

## 五个机会假设——不是“全网无人做过”的断言

以下由上述接口能力及用户的实时空间需求推演，尚无采用率和独特性证明。建议用任务完成时间、纠错次数、结果真实性来验证，不能只看演示动效。

| 机会 | 用户真正遇到的问题 | 组合与眼前一亮的时刻 | 验证方式 |
|---|---|---|---|
| **缺什么，就长出什么控件** | 一句含糊的话往往换来长问卷或泛泛回答 | 输入“股票咋样”时先出现市场/关注对象的极简选择；输入“新能源，近一个月”后，这两个缺口消失，真实数据、比较和事件联动出现。组合：意图判断＋缺失条件判断＋数据连接器＋动态视图 | 与普通聊天比较：首次获得相关真实内容所需步骤；错误猜测率。行情取数和事实核验另有接口负责 |
| **改一个条件，只更新受影响的部分** | 补充条件常导致整页重做，用户选择、编辑内容和位置丢失 | 行程中把“周六”改为“周日”，天气、营业时间和路线重算，已写的同行说明保留。组合：变更类型判断＋对象指代＋依赖图＋局部更新 | 用连续五次改口测试：保留已编辑内容、正确失效依赖、无过期结果覆盖；稳定性比刷新频率重要 |
| **乱资料自动对齐，只露出值得处理的差异** | 真正耗时的是不同表、订单、附件名字和字段不一致，难发现遗漏 | 放入订单和到货清单，自动对应“同一件商品”的不同叫法；数量用代码精确核对，只展开短缺、重复或不确定的行，并可点回原证据。组合：实体匹配＋字段映射＋精确运算＋异常视图 | 人工标注一批真实格式差异，比较漏报、误配及核对时间；所有改写先有可撤销预览 |
| **作品边做，依据边跟上** | 写报告、方案时数据改了，结论、表格和引用容易不同步 | 修改一项核心数据，相关图表重算，受影响的结论出现待更新标记；不相关段落不动。组合：来源绑定＋语义支持判断＋依赖追踪＋局部内容生成 | 故意改数字、来源和适用条件，检查是否准确定位影响范围；不能仅凭 Jev 一次判断承诺事实正确 |
| **行动做完，系统回来验证它有没有用** | 大部分分析到生成待办就断了，用户无法知道建议是否奏效 | “下周减少库存积压”产生关联具体 SKU 的行动；导入下一周数据时，自动对齐原问题、措施和实际变化，保留未能证明因果的状态。组合：异常识别＋行动关联＋持久上下文＋后续观测＋变化视图 | 连续两个真实工作周期测试：用户是否少做一次手动复盘，是否能区分变化、相关和因果 |

优先验证前两项：它们最直接对应“每个字都改变正在用的界面”，并能暴露模型选择、真实数据、组件状态和调度是否真正连通。第三项最容易找到明确的节省时间证据。第四、五项更适合空间已能保存对象关系后的阶段。

## 来源与账本边界

- 全文已通过免费 `dr.record_fetch(..., backend='direct')` 进入共享 `fetches.jsonl` 与缓存；相关观察见 `observations.jsonl`，agent=`ecosystem_analysis`。
- 生态统计只有论文单源，本文均使用“作者报告”，不得转述成已独立验证的生态事实。方法、官方限制同样以来源自身陈述归属，不泛化为所有版本及本地 KEV。
- “结构正确不保证语义正确”有官方 docs.typesafe.ai 与独立 arxiv.org 两域证据；其余具体统计不能用转载同一论文冒充独立佐证。
- 预印本不是商业运行审计。此次仅阅读证据，没有运行或重新 benchmark 任一模型。
- 技术性检索中出现多个与官方名称相近的独立域名；能力与限制的依据只取官方 docs.typesafe.ai 和原始研究。
